## Theme

v1.0.0 is a **memory, ledger & configuration** release. It stops the language from dictating a memory
architecture and instead makes memory a *configurable substrate behind two agentic seams*,
sharpens the line between the **ledger** (objective, deterministic, untainted record of events)
and **private memory** (subjective, agentic, tainted belief), adds **causal traversal** of the
ledger, and pins down **durability/crash-recovery** via the ledger as a write-ahead log. A
secondary thread (from a fact-checking design exercise) records an open **graded-aggregation**
gap.

Guiding principle that recurs throughout: **the language owns the contract at each membrane;
the substrate owns the mechanism.** This is the same discipline already applied to the provider
(cognition) and tools (the world); v1.0.0 extends it to memory and makes the ledger its dual.

## 1. Memory is a configurable substrate (a port), not a built-in architecture · §10

- **Decision.** Demote the §10 SQL/vector/graph trio from "the memory model" to "the capabilities
  the *default Rust runtime's* substrate happens to advertise." The chapter becomes the **port
  contract**. Memory joins provider/tools/principal as a fourth governed membrane.
- **Contract the language keeps (every substrate must honor):** trust typing of reads (§3);
  journaling/replay of agentic reads (§15.4.2); provenance to the ledger (§10); capability-gating
  (§13).
- **Mechanism the substrate owns (swap freely):** physical storage, indexing, retrieval
  algorithm, whether `store` decomposes/embeds/keeps-verbatim, eviction/TTL, and **which
  query modalities exist**.
- **Consequence.** Substrate capabilities become an **interface/capability contract** (rides on
  the v1.1.0 interface work): a program either targets the minimal core or *declares* the memory
  capabilities it requires, checked at bind time. Binding a substrate that can't serve a
  requested return shape is a load-time error, not a runtime surprise.
- **Rationale.** Memory architecture is an open research question (Temporal, mem0, Zep/Graphiti,
  GraphRAG, markdown-file memory…). Under-specifying mechanism is correct, exactly as `<-` does
  not freeze "how to prompt."
- **Config selects substrate ONLY; semantics are intrinsic.** The manifest's `[memory]`/`[ledger]`
  sections pick the backend and nothing else. Memory recall is *always* tainted, the ledger *always*
  exists and is *always* recorded-trust, and `store`/`recall` is *always* the interface — so
  `trust`, `capabilities`, durability, and "does it exist" are NOT config knobs; they are language
  semantics. Putting them in config is the same smell as putting data in the grammar. (Durability is
  implied by *which* substrate you pick, not a separate flag.)
- **Prose/markdown is a representation, not a modality.** SQL/graph/vector are *retrieval
  structures*; "raw text" is a *representation* (kept whole vs decomposed) — orthogonal axes. Raw
  text can live in a SQL column, a vector doc, a graph node, or a file, so there is no "md + sql +
  graph + vector" default list to bless: the language sees only `store`/`recall` over values, and
  "store raw text in whatever medium" is entirely the substrate's business. Distinct from
  `instruction` (§4): an `instruction` is fixed *behavioral* prose (source, settled,
  change-by-release); a runtime "jotted note" is *content* prose in memory (agentic, tainted on
  recall). Agents can jot prose — it lands in tainted memory, never in settled source.

## 2. The memory surface: two seams + handles (`mem`) · §10

- **Remove** `find` / `select` / `match` from the *private-memory* surface (they survive only over
  the ledger — see §7 below — because the ledger's schema is language-defined).
- **Keep two agentic seams + a handle type `mem`:**
  - `mem m <- value` — write/create; `m` references the substrate artifacts the write produced.
  - `m += value` — augment the region.
  - `text t = m -> "query"` — recall (read out of the region).
  - `forget m` — drop the region (see §6).
  - `say(m)` / `m.count`, `m.origin` … — runtime metadata accessors.
- **`store(x)` / `recall(q)` become sugar** for the agent's implicit default `mem`.
- **Operator story.** `LHS <- RHS` = "ingest RHS into the seam LHS" — an *agent* on the left
  thinks (provider); a *mem* on the left stores (memory). `->` reads out of a mem. The arrow
  **asymmetry encodes durability**: cognition is transactional (one arrow), memory is durable so
  write-moment and read-moment are distinct (two arrows). Disambiguation is type-directed on the
  LHS.
- **Supersedes** the earlier `note`/`recall` sketch: verbatim-vs-decomposed is now a *substrate*
  choice for `store`, not a second write verb.
- **Integration note.** Handle-oriented memory matches real APIs (mem0 add/search/delete, vector
  namespaces, Graphiti episodes) better than free functions do.

## 3. Memory trust: a recall is always tainted · §3, §13

- **Decision.** Drop the trust-typed-container idea (`mem<settled>` — trust is a *lattice on
  values*, not a type parameter). **Memory stores anything; every recall comes out tainted**,
  because memory is agentic.
- **Rule:** a recall is **taint-equivalent to a send** — `->` behaves like `<-` on the trust axis
  (tainted; re-gate before any consequential sink). No store-side trust enforcement.
- **Why it's cleaner.** Nothing leaves memory `settled`, so there is no laundering path; the
  read-side rule alone closes the hole that the container approach needed write-side checks for.
  Zero new trust machinery — it reuses the existing send-taint rule.

## 4. `instruction` — procedural memory lives in source, not memory · new statement; §5, §9

- **Decision.** Add a top-level `instruction "…";` statement = the **compile-time system prompt**.
  Procedural knowledge (how to behave) is *source/code*; accumulated knowledge (facts) is the
  memory port (§1). This resolves the earlier conflation of the two.
- **Scoping.** Top-level `instruction` = global default; an `instruction` inside an agent body is
  agent-scoped and **composes after** the global block (fixed order, for determinism). `extend`
  **inherits and appends** (append-only — you cannot silently weaken a parent's guardrails;
  override is a later, explicitly-marked escape hatch — *open*).
- **Trust/security.** Instructions are `settled`-by-origin (source). Security property worth
  stating explicitly: **an agent's behavioral spec cannot drift without a versioned, reviewable
  release** — no recalled fact or injected memory can rewrite the system prompt, because the
  system prompt is not in mutable memory. "When instructions change → ship a new version" is the
  intended workflow, not a limitation. The declined capability (runtime self-modification of
  instructions) is an anti-feature for a governance language.

## 5. The ledger is not memory — they are distinct stores · §10, §15.4.2a

- **Correction.** The ledger is the global, append-only **audit log of every event**; private
  memory is each agent's own store. A `mem` handle points at *private memory*, never at the ledger.
  The ledger *references* memory operations (the `Internalized` event, provenance backpointers) for
  audit and as a WAL, but the memory *data* lives in the substrate. (WAL relationship, not
  identity — like a database's log is not the database.)
- The ledger therefore keeps **none** of `<-` / `->` / `+=` / `forget`. It is not a read-only
  `mem`; it is a categorically different thing with its own verbs (§7, §8).

## 6. `forget` = tombstone, not erasure · §6, §10

- `forget m` appends a `Forgotten` event making the region unrecallable going forward; the
  historical record stands (an audit log cannot lie about its past — cf. §6 expiry tombstone).
  Physical/crypto erasure (GDPR) is a *substrate capability* invoked under the tombstone.
- **Open:** does `forget` **consume** the handle (linear; later use is a compile error — leaning
  this way) or tombstone-and-leave-empty?
- **Open:** deletion is the only non-read/write memory op; is it the third verb, or "a write the
  substrate interprets"? Leaning: keep the surface at two write verbs + `forget`.

## 7. Querying the ledger: reuse `select … from ledger` (deterministic, untainted) · §7, §10, §15.4.2a (E-Query-Stmt)

- **Decision.** The ledger keeps a *deterministic* query, distinct from agentic recall, because the
  ledger is not agentic. **Reuse the existing v1.0.0 surface — `select … from ledger where { cond }`
  (flat filter) and `find … where { triple+ }` (relational/causal, §8) — do NOT invent a keyword.**
  (An earlier draft proposed `scan` mirroring `when`; dropped as redundant with `select … from
  ledger`.)
- **`find`/`select`/`match` are therefore NOT deleted in v1.0.0 — they are relocated to ledger-only**
  (and capability-advertising substrates), removed only as the *mandatory private-memory* surface
  (§2). The ledger can carry them because its schema is language-defined; an opaque memory substrate
  cannot, so it gets only `<-`/`->`.
- A ledger query is **deterministic, untainted (recorded trust), and appends nothing** (the expr
  form; replay re-folds the same prefix — E-Query-Stmt). `when` remains the *prospective* dual
  (future events); the `select`/`find` queries are *retrospective*.
- **Trust asymmetry vs memory (the load-bearing distinction):** ledger reads carry **recorded
  trust** — a `Decided` the gate endorsed reads back `settled`, because the ledger *is* the proof
  it was endorsed; memory reads are always tainted. The split is exactly *objective record vs
  subjective belief* (§10 of this doc).
- **No `ledger -> "prompt"`.** An agentic interpretation of the log is composed, not primitive: a
  deterministic ledger query (untainted) → feed the result into a `<-` send (the seam taints the
  *result*, correctly).
  Each operator keeps exactly one trust behavior; taint enters only at the cognition seam.
- **Property:** the ledger records *commitments and effects* (decisions, emits, tool results,
  attestations) — **not raw un-endorsed thoughts** (per E-Send, raw replies are not logged, only
  their lifecycle). The queryable record is "what was decided and done," which is why ledger reads
  are safe to treat as recorded-trust.

## 8. Traversing the ledger: causal lineage as a query (not accessors) · §10 (`find`), §15.4.2a

- **Motivation.** A flat ledger query gives *topical* sets ("all decisions about alice"); it does not
  follow *derivation*. "Which decisions did this one come from / result into?" is a **third
  relation** — causal lineage — distinct from tick/hash order (sequential, tamper-evidence) and
  subject grouping (topical).
- **Coupling principle (load-bearing).** The language couples to the ledger's *semantic model* (an
  append-only, queryable, causally-linked event log — already true of `when (Decided d)`), **never
  to its physical schema** (fields, columns, edge labels). `causes` is therefore **a reserved
  relation label in ledger *data*, NOT a grammar keyword** — predicate-position names in `find … where`
  are data the graph engine matches, not reserved words. Consequences: a new ledger **field** is
  queryable by generic `select … from ledger`; a new **edge type** later (`supersedes`, …) is a new
  data label queried by the same generic `find` — **zero grammar change either way**. Querying a
  field/edge a runtime doesn't provide is a **bind-time capability error, not a version break**;
  old programs are unaffected (additive). This is the SAME capability-contract treatment given to
  memory substrates (§1) — the ledger advertises its queryable fields/relations as a capability
  surface — applied to one more store, not a ledger-specific rule.
- **Decision (revised again — no reserved causal label).** The language **blesses no causal
  relation name** (`causes`/`effects` rejected). Two reasons: a reserved relation freezes ledger
  semantics (a new edge type → a language edit), and it imports English grammar (`causes` is
  3rd-person-singular; `{ events causes x }` is ungrammatical — formal queries can't carry
  subject-number agreement). The deeper rule: **the language blesses *operations* (bare uninflected
  verbs — `attest`, `emit`, `store`, `forget`), never *relation vocabulary*. Relation labels are
  data.** Causal traversal therefore uses only constructs that already exist:
  1. **Generic graph query** `find … where { s p o }`, where the edge label `p` is **data** resolved
     against the queried graph's advertised schema — exactly as relationship-memory predicates
     already are (they come from internalization; none are hardcoded). The ledger is one such graph;
     its edge labels (causal and otherwise) are ledger-schema data, evolvable without a language
     change, advertised as a capability surface (§1).
  2. **`origin()`, generalized** (already in v1.0.0: `find n, origin(n) where {…}`) — a **noun**
     accessor (no conjugation, no subject agreement) returning backward provenance ("what produced
     this"), generalized from memory cells to any ledger event. Backward/common case needs no new
     vocabulary.
  - Forward and richer causal queries = the generic graph query over data edge-labels; the canonical
    causal label lives in the **runtime/stdlib convention layer** (versioned independently; by
    convention an uninflected noun), NOT the core language.
- **Still predicate *form*, not dot notation** — but the predicate *name* is data, not a reserved
  word. The earlier dot-notation sketch (`d.causes`) stays rejected: no array filter (a dot-accessor
  bag can't be narrowed; §15.2), arrays don't chain for multi-hop, and it needs a universal `Event`
  supertype (collides with prelude `Event(text)`). Dot notation stays for **intrinsic event
  attributes** (`d.amount`, `e.subject`); graph queries handle **relations between events**.
- Transitive closure is a **bounded** library walk over `origin` — no unbounded loops in the kernel.
- **Definition (well-formed from the operational semantics):** *B is an immediate cause of A iff a
  value B produced or recorded was consumed by the step that appended A.* Examples: a `Decided`'s
  cause = the event producing the gated `Credence`; an action's cause = the authorizing `Decided`;
  `ToolResolved`'s cause = its `ToolStarted` + argument-producing events.
- **Status of the data.** The DAG is *reconstructible today* (event `src` subjects + `corr` ids +
  producer→consumer value flow), but only **implicit**; v1.0.0 makes `causes`/`effects` first-class
  predicates. Generalizes §10's `origin(n)` (single backpointer) to a full walk.
- **Implementation note.** Backward edges are free from `src`; **forward (`effects`) needs a runtime
  reverse index.**
- **Reuse.** Same causal DAG the referenced Multi-verse fork/merge and counterfactual replay
  (Jefferson *Time Warp*) already need.

## 9. Durability & crash recovery: the ledger is the WAL · §15.4.2, §15.5, §5

- **Ledger durability is non-negotiable** — it is both the audit record and the write-ahead log. A
  persisted ledger ⇒ recovery + audit; an ephemeral ledger ⇒ "dev/test" mode where a crash forgets
  everything.
- **Memory durability is a substrate property**, with two recovery models:
  1. **Volatile substrate, rebuilt from ledger** — replay the ledger's memory operations
     (decompositions are re-served from journaled results, not re-run as cognition).
  2. **Durable substrate, reconciled** — substrate persists itself; on restart, replay only the
     ledger memory-events newer than its last checkpoint, **idempotently (keyed by event id)**.
- **Answer to "do agents forget on crash?": No, iff the ledger is durable.** The ledger is what
  reconstructs or reconciles memory.
- **Dual-write consistency** resolved by the WAL discipline: append intent to the ledger *first*,
  then apply to the substrate idempotently; on restart, converge the substrate to the ledger. A
  substrate that can't do idempotent keyed application is forced into the volatile/rebuild model
  (the port contract expresses the requirement).
- **Recovery = reawake-from-ledger**: re-awakening a recovered agent is a *reawake*, not a
  *first-awake*, so the constructor does not re-run (`agent_reawake_no_reconstruct`); `E-Crash` is
  a contained fault, not a death. Restart replays the ledger to reconstruct the configuration
  (agents, memory, pending messages), then continues appending. (Agape was already event-sourced;
  durability falls out of the existing replay model.)

## 10. Ledger as mediator; epistemics; visibility · §6b, §7, §15.4.2a

- **Effects are ledger-mediated (no quiet side-effects).** Every effect — tool call, send, **and
  memory write** — is a request *appended to the ledger*; the runtime is the sole executor; results
  fold back as events. One totally-ordered log ⇒ concurrency collapses to append-order ⇒ **no
  races**, deterministic replay, full audit, recovery. Memory writes being ledger-mediated is the
  WAL discipline (§9) restated.
- **Blockchain framing (already in §15.4.2a, recorded here for completeness):** the ledger is the
  *transparency half* of a blockchain (hash-linked Merkle, append-only, tamper-evident); the
  *consensus half* is absent in a single runtime (one writer assigns ticks) and becomes
  load-bearing only at the **distributed-distrust boundary** (multiple mutually-distrusting
  runtimes sharing one ledger — optional layer).
- **Epistemics (the useful reframe):** ledger = **objective shared record of events** (consensus on
  *what happened*); private memory = **subjective divergent belief** (agents diverge on *what it
  means*). This split *generates* the two trust rules (recorded vs tainted).
- **Visibility:** default the ledger to a **public commons** (readable across agents in a
  single-owner fleet); privacy lives in private memory, not ledger ACLs. Partitioning / encrypted
  entries (the private-transaction analog) belong at the distributed-distrust boundary — the same
  boundary where consensus enters. Transparency and consensus arrive together, at the edge, or not
  at all.

## 11. (Secondary) Graded aggregation over non-`bool` credences — OPEN · §12

- **Finding (from a fact-checking design exercise).** Fusion/quorum (`all`/`any`/`quorum`) are
  defined only over `Credence<bool>`. Evidence-grounded fact-checking's native judgment is
  `Credence<Entailment>` (three-valued: `Entails` / `Contradicts` / `Neutral`, because "no
  evidence" ≠ "refuted"). Aggregating many such judgments forces a lossy choice: reduce-to-bool
  then fuse (loses Contradicts vs Neutral), or gate-each then boolean-combine (loses the single
  fused certificate; gates N times early).
- **Candidate primitive.** A dependence-aware, three-valued reduction over `Credence<E>` (a
  Kleene-style meet for `Entailment`: all-`Entails` ⇒ `Entails`; any-`Contradicts` ⇒ `Contradicts`
  (veto, fires the answer-level `Contradiction`); else `Neutral`), yielding one fused `Credence<E>`
  to gate once. Preferred over forcing log-odds fusion onto arbitrary enums (binary math doesn't
  generalize soundly).
- **Status.** Surfaced, not designed. Lower priority than the memory/ledger work; recorded so it
  isn't lost.

## 12. Configuration & gate-provider integration · §3, §16.8, §17

**The "fix the lazy configs" cleanup — one rule across every backend.** Config selects a *backend*;
the backend's *capabilities* are intrinsic (never user knobs); *secrets* bind from env (never the
manifest). The same principle we set for the ledger/memory substrates, now also covering the
provider:

| seam | manifest selects | capability (intrinsic, derived) | secret (env) |
|---|---|---|---|
| ledger | `[ledger] substrate` | durable? ordered? | (backend creds) |
| memory | `[memory] substrate` | modalities; always agentic/tainted | (backend creds) |
| gate provider | `[provider] backend + model` | **`exposes_logprobs`** → logprobs vs sampling | API key |

- **`exposes_logprobs` is DERIVED, not set.** The agape-hello manifest's hand-set
  `exposes_logprobs = true` was the laziness: it is a *capability of the chosen backend*, not a knob.
  `anthropic` ⇒ false (→ sampling fallback, §16.8); `openai`/`gemini` ⇒ true (→ token-mass
  `Credence`, §3). Setting it by hand is the same smell as putting trust/data where it doesn't
  belong.
- **Secrets never in source/manifest.** API keys bind from env (`ANTHROPIC_API_KEY` /
  `OPENAI_API_KEY` / `GEMINI_API_KEY`), per §3's declared-dependency discipline ("no endpoint or
  secret appears in source"). The manifest names backend + model; auth is bound outside.
- **Sampling knobs are conditional.** `samples` / `temperature` (§16.8) apply ONLY to a no-logprobs
  backend, and are meaningless under a logprobs backend.
- **Gate provider ≠ orchestration model.** This provider feeds the GATE (the `Credence`'s calibrated
  mass), not the agent loop — §3: the gate's number is token mass on the forced choice, not the
  orchestrator's self-rating. You may orchestrate with one model and gate with another.

**The three backends (verified 2026-06):**

| backend | logprobs? | path | enable | response → per-option mass | default model |
|---|---|---|---|---|---|
| **anthropic** | NO | sampling fallback (§16.8) | N draws @ temp | empirical frequency | `claude-haiku-4-5` |
| **openai** | yes (`top_logprobs` ≤ **5**; non-reasoning models only) | token mass | `logprobs:true, top_logprobs:N` | `choices[].logprobs.content[0].top_logprobs[]` {token, logprob} → `exp`, renormalize | `gpt-4o-mini` |
| **gemini** | yes (`logprobs` ≤ **20**) | token mass | `responseLogprobs:true, logprobs:N` (+ enum mode) | `candidates[].logprobsResult.topCandidates[].candidates[]` {token, logProbability} | `gemini-2.5-flash` |

- **Per-backend adapter (the "not easily swappable" reality).** One interface, three adapters =
  `(request builder, response → [{option, logprob}] extractor, renormalizer)`. Divergences absorbed:
  param names (`top_logprobs` vs `responseLogprobs`+`logprobs`), top-N ceiling (**5 vs 20**), nesting
  (`content[].top_logprobs[]` flat vs `logprobsResult.topCandidates[].candidates[]` nested), field
  name (`logprob` vs `logProbability`), constrain-to-set (OpenAI bare single-token / `logit_bias` /
  json_schema vs Gemini `text/x.enum` mode — Gemini enum+logprobs is the cleanest).
- **Single-token variant rule (a real gate constraint, → spec note on §3).** Logprobs are per-token,
  so each `Credence<E>` variant must map to a distinct *leading* token to read its mass at position
  0. `bool` (true/false) and small enums are fine; multi-token labels (e.g. `Contradicts`) need
  enum-mode (Gemini) or first-token handling. Practical variant-set cap: OpenAI ≤5, Gemini ≤20.
- **Anthropic temperature caveat:** Opus 4.7/4.8 & Fable 5 reject `temperature` → a
  temperature-knobbed sampling fallback must use Haiku 4.5 / Sonnet 4.5.
- **SDKs:** `@anthropic-ai/sdk`, `openai`, **`@google/genai`** (NOT the deprecated
  `@google/generative-ai`).
- **Build order (this release, per doc→test→implement):** documented here → conformance tests
  (backend selection; `exposes_logprobs` derived not set; logprobs vs sampling path; variant-cap;
  secret-from-env) → implement the adapters in the agent-server (**OpenAI first, then Gemini**;
  Anthropic sampling already exists).

## Lexical & conformance impact · §2

- **Reintroduce `->`** (a retired `LexError` in v1.0.0) for memory recall, **type-directed**: valid
  on a `mem`, rejected on an agent. `lex_reject_right_arrow.ag` flips from `LexError` →
  `TypeError` (agent `a -> "…"` is now a type error, not a lex error).
- **New keywords:** `mem`, `forget`, `instruction`. (No `scan` — ledger queries reuse `select … from
  ledger` / `find … where`.) Verify none collide with the contextual-identifier rules (§2).
- **No reserved causal vocabulary** (revised): the language blesses **no** causal relation name —
  not as a keyword, not even as a reserved data label. Causal traversal rides the generic graph
  `find … where { s p o }` (edge label = data) plus the existing `origin()` noun-accessor. New ledger
  fields/edges are *data*, queryable generically — they never bump the grammar or the language
  version (§8). The ledger's queryable fields/relations are a runtime **capability surface**, checked
  at bind time like a memory substrate's (§1); the canonical causal label is a stdlib/runtime
  convention, versioned independently of the core language.
- **Principle:** the language defines **operations** (bare uninflected verbs) and **generic
  mechanisms** (+ noun accessors like `origin`); it defines **no domain/relation vocabulary**.
  Blessing a relation name is the smell that data is leaking into the grammar.
- **`find`/`select`/`match` retained** (relocated to ledger + capable substrates), NOT removed from
  the lexer; only dropped as the mandatory private-memory surface.
- **New events:** `Forgotten` (tombstone); confirm `Internalized` / `QueryResult` coverage for
  `store` and ledger queries.
- **New conformance tests implied:** recall-is-tainted (re-gate before sink); `forget` consumes (if
  linear); ledger `select`/`find` are untainted + append-nothing; `find … where { d causes a }`

## Open questions (carry into spec drafting)

1. `forget`: consume (linear) vs tombstone-and-empty.
2. `instruction` under `extend`: append-only vs marked override.
3. Three-valued aggregation (§11): primitive shape, or leave to a library.
4. Transitive lineage closure: bound, or lazy/streaming handle.
5. Memory capability interface: minimal required core vs fully-declared requirements.
6. Graph `find` source designation: since edge labels are now plain data (no ledger-only predicates),
   `find` needs an explicit way to say *which* graph — the ledger causal DAG vs an agent's
   relationship graph (a `from ledger` clause?). Also: the type-narrowing predicate syntax
   (`a is Action`?), and the canonical causal edge label as a stdlib convention.
7. **RESOLVED — renamed `spine` → `ledger`.** It is a reserved *identifier* (the dual of `self`:
   self = subjective local agent, ledger = objective shared record), not a grammar keyword — nothing
   constructs it; it is grown by every appending op. (`history` was the runner-up; `ledger` chosen
   for the audit/append-only/blockchain framing.) Remaining: global rename in SPEC.md when drafted.
